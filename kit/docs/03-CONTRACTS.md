## §3 Coming-soon page and preview bypass (`proxy.ts` / `middleware.ts`)

**Applies** to every request when `HOLA_COMING_SOON=1`, **except**:

- `/admin` and everything under it (the admin has its own login, §18), `/api/…`, `/_next/…`
- `/favicon.ico`, `/icon.svg`, `/apple-icon.png`, `/manifest.webmanifest`, `/robots.txt`, `/sitemap.xml`
- static files under `/brand/`, `/fonts/`, `/images/` and any other `public/` file
- requests with a valid admin session or a valid preview cookie (below)

**Admin session:** the `hola_session` cookie (§18) is valid only when its JWT verifies against `APP_SECRET` (HS256, `jose`) and is not expired. The interceptor checks only the signature and expiry. A cookie that is present but invalid (e.g. `hola_session=garbage`) is treated as a visitor.

**Preview bypass:**

- `GET <any page>?hola_preview=<HOLA_PREVIEW_KEY>` responds `307` to the same URL without the parameter and sets cookie `hola_preview` = hex `HMAC-SHA256(key=APP_SECRET, msg="preview|" + HOLA_PREVIEW_KEY)`; `Path=/`, `HttpOnly`, `SameSite=Lax`, `Max-Age=2592000`, `Secure` only on HTTPS.
- A wrong key sets no cookie and gets the coming-soon page.
- A request whose `hola_preview` cookie equals that HMAC is served normally.

**The coming-soon response:**

- Status `503`; headers `Retry-After: 86400`, `X-Robots-Tag: noindex, nofollow`, `Cache-Control: no-store`.
- A self-contained HTML page: `<html lang="es">`, `<title>Hola Egipto · Muy pronto</title>`, `<meta name="robots" content="noindex,nofollow">`, the stacked colour logo, the line `Muy pronto · Coming soon`, one sentence in each language, `papyrus` background, brand fonts.
- A WhatsApp button only when `whatsapp_number` is set.

## §4 Content model (MySQL via Drizzle)

**Engine:** Hostinger's MySQL service (MySQL-compatible; may be MariaDB — record `SELECT VERSION()`). Locally: MariaDB from Ubuntu's `mariadb-server`. Write SQL that runs on **both MySQL 8 and MariaDB 10.6+**:

- `utf8mb4` / `utf8mb4_unicode_ci` on every table.
- Drizzle `mysql-core` dialect. **No native `json` columns:** store structured values in `longtext` through one custom Drizzle type `jsonText<T>()` (stringify on write, parse on read), because MariaDB returns JSON as text.
- No CHECK constraints, generated columns, `RETURNING`, or functional indexes.
- **No `.default()` on `text`/`longtext`/`jsonText` columns** (MySQL 8 rejects literal TEXT defaults); set those defaults in the data layer.
- **Charset:** Drizzle does not emit a table charset; tables inherit the database default, which must be `utf8mb4` (the README and docs/07 create/check it). Do not hand-edit generated SQL for this.
- **Never edit or regenerate an applied migration**; add a new one. A full local reset drops all tables including `__drizzle_migrations`.
- `varchar` lengths: slugs 191 (index limit), titles 255.
- Booleans as `boolean` (tinyint(1)). Timestamps as `datetime` stored in UTC.

**Localization:** two locales, `es` (default) and `en`, no fallback. **Facts are shared, words are localized.** Every entity with text has a main table (shared fields) and an `<entity>_i18n` table: `entity_id` (FK, `ON DELETE CASCADE`), `locale` (varchar(2), `es` \| `en`), `available` (boolean), and every localized field. Unique keys: (`entity_id`, `locale`) and (`locale`, `slug`).

- **Shared** (main table): prices, durations, group sizes, dates, availability days, gallery, relationships, `featured`, `booking_mode`, `booking_url`, coordinates, `hola_sample`, `created_at`, `updated_at`.
- **Localized** (`_i18n`): `title`, `slug`, `excerpt`, `content`/`overview`, `subtitle`, `highlights`, `itinerary`, `includes`, `excludes`, `what_to_bring`, `season_note`, `price_note`, `faq`, `seo_meta_title`, `seo_meta_description`, and every other free text in spec §5.
- Lists (highlights, itinerary, includes, faq, cabins, start dates, top sights, gallery ids…) are `jsonText` columns in the table matching their language rule.

**Rich text:** `content` / `overview` are **Markdown** (`longtext`), rendered on the server by one renderer (`src/lib/markdown.ts`, e.g. `marked`) and sanitized (`sanitize-html`, allow-list). Two shortcodes for guides: `[[trip-card:<tour|cruise|excursion>:<id>]]` (renders the trip card) and a `:::tip … :::` block (renders the Tip box).

**Relationships:** many-to-many and ordered relations are **join tables** with foreign keys and a `position` column where order matters (e.g. `trip_destinations`: `trip_type`, `trip_id`, `destination_id`, `position`; `related_trips`: `owner_type`, `owner_id`, `trip_type`, `trip_id`, `position`). Single references are FK columns.

**Field names:** the **logical** field names below are the spec §5 names verbatim and are what `hola:schema` reports (§9); physical columns use the same snake_case names. Logical-to-physical mappings: `holaSample` ↔ `hola_sample`; `seo` ↔ `seo_meta_title`, `seo_meta_description`, `seo_og_image`; images `alt` ↔ `alt_es`, `alt_en`; inquiries `trip` ↔ `trip_type`, `trip_id`; relationship names ↔ their join tables.

## §6 Language rules

- `<html lang>` is `es` or `en`.
- The language switcher links to the same item in the other language, and is hidden on a page whose item is not `available` in the other language.
- Prices: EUR on Spanish pages, USD on English pages, from `price_from_eur` / `price_from_usd`. ## §7 Inquiry API

**Token** (reusable within its validity window, not single-use): `GET /api/hola/token` → `200 {"token":"<ts>.<hmac>"}` with `Cache-Control: no-store`. `ts` is Unix seconds; `hmac` is hex `HMAC-SHA256(key=APP_SECRET, msg="inq|" + ts)`. Valid when its age is between 3 s and 48 h.

**Endpoint:** `POST /api/hola/inquiry`, body JSON (`Content-Type: application/json`) or form-encoded (`application/x-www-form-urlencoded`, the no-JavaScript path).

| Field | Rule |
| --- | --- |
| `form` | `plan_my_trip` (default) \| `contact` |
| `lang` | required, `es` \| `en` |
| `token` | required, valid |
| `website` | honeypot, must be empty |
| `name` | required, 2–80 characters |
| `email` | required, valid email |
| `consent` | required, `1` |
| `adults` | required for `plan_my_trip`, integer 1–30 |
| `trip_id` + `trip_type` | optional; must point to an `available` tour/cruise/excursion (`trip_type` = `tour` \| `cruise` \| `excursion`) |
| `interests[]`, `length`, `date_mode` (`exact` \| `month` \| `flexible`), `date_from`, `date_to`, `month`, `children`, `children_ages`, `budget`, `hotel`, `group_type`, `whatsapp`, `channel` (`whatsapp` \| `email`), `message` (≤ 2000), `marketing`, `page_url`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`, `landing` | optional |
| `cf-turnstile-response` | required only when both Turnstile keys are set; verified server-side |

**Turnstile keys empty:** accepted when `HOLA_DEV_MODE=1`; otherwise answered `400 {"ok":false,"errors":{"form":"…"}}`.

**JSON responses:**

| Status | Body | When |
| --- | --- | --- |
| 201 | `{"ok":true,"id":<id>,"redirect":"<thank-you path in lang>?ref=<ref>"}` | valid |
| 422 | `{"ok":false,"errors":{"<field>":"<message in lang>"}}` | validation failed |
| 400 | `{"ok":false,"errors":{"form":"…"}}` | honeypot, bad/expired token, Turnstile |
| 429 | `{"ok":false,"errors":{"form":"…"}}` | more than 5 per `ip_hash` per hour |

**Form-encoded responses:** valid → `303` to the thank-you URL with `?ref=`; invalid → `303` back to `page_url` (or the form page) with `?errors=<comma-separated field names>#form`.

**Rate limit bypass and test flag:** when `HOLA_DEV_MODE=1` and the request has header `X-Hola-Test: 1`, the rate limit is skipped and the stored inquiry gets `holaSample: true`.

**Storage** (`inquiries` table, through the data layer): title `{name} · {trip title | "Sin viaje"} · {YYYY-MM-DD HH:mm}`; fields `form`, `trip_type` + `trip_id`, `interests`, `length`, `date_mode`, `date_from`, `date_to`, `month`, `adults`, `children`, `children_ages`, `budget`, `hotel`, `group_type`, `name`, `email`, `whatsapp`, `channel`, `message`, `consent_at`, `marketing`, `lang`, `page_url`, `utm` (jsonText: `source`, `medium`, `campaign`, `term`, `content`), `gclid`, `fbclid`, `landing`, `status` (`new` default \| `replied` \| `won` \| `lost`), `tracked` (boolean), `ip_hash` (hex SHA-256 of IP + `APP_SECRET`), `holaSample`.

**Ref:** `<id>.<hex HMAC-SHA256(key=APP_SECRET, msg="ref|" + id)>`.

**Thank-you tracking:** the thank-you page renders the `generate_lead` push only when `ref` is valid and the inquiry's `tracked` is false, then sets `tracked` to true. The page is never cached.

**Mail** — every message goes through one function, `sendMail()` in `src/lib/mail.ts` (nodemailer over SMTP):

- **Team:** to `contact_email` (fallback `ADMIN_EMAIL`), `Reply-To` the traveller, all fields listed.
- **Traveller:** an auto-reply in their language with `reply_hours`.
- **While `HOLA_DEV_MODE=1`:** the recipient is replaced by `ADMIN_EMAIL`, the subject is prefixed `[DEV → <original recipients>]`, Cc/Bcc are dropped.
- If `SMTP_HOST` or `SMTP_PASS` is empty (or, in dev mode, `ADMIN_EMAIL`), nothing is sent and the log says `to=(not-sent)`. A send failure is logged and never fails the inquiry.
- **Every call** appends one line to `HOLA_MAIL_LOG`: `<ISO time>\tto=<final recipient or (not-sent)>\torig=<original recipients>\tsubject=<subject>`.

**Webhook:** if `N8N_WEBHOOK_URL` is set, POST the inquiry as JSON (id, created_at, lang, form, trip {id, type, title, url}, all fields, utm) after the response is sent (`after()`), timeout 5 s, header `X-Hola-Signature: sha256=<hex HMAC-SHA256(key=HOLA_WEBHOOK_SECRET, msg=body)>`.

**Retention:** `pnpm hola:retention` deletes inquiries older than 24 months whose `status` is not `won` (run by hand from WSL with `--env=hostinger`, §19).

## §8 WhatsApp

`whatsappUrl(ctx)` in `src/lib/whatsapp.ts` returns `https://wa.me/<whatsapp_number>?text=<encodeURIComponent(message)>`.

- **Message:** `whatsapp_message_default` in the page language. On trip pages: ES `Hola, me interesa «{title}» — {url}`, EN `Hi, I'm interested in “{title}” — {url}` (`{url}` absolute).
- **Always** include `?text=` (the generic message when there is no trip), on every placement including the header.
- **Number empty:** no WhatsApp link or button is rendered anywhere (the layout keeps its shape).
- **Every rendered link** carries `data-he-event="whatsapp_click"`, `data-he-location="<header|sticky|sidebar|page|footer|coming_soon>"`, and `data-he-trip="<id>"` when there is a trip.

## §11 Security behaviours

- `poweredByHeader: false` (no `X-Powered-By`).
- Every front-end response has `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, `X-Frame-Options: SAMEORIGIN`, and `Content-Security-Policy-Report-Only`.
- **Admin protection:** every `/admin…` page except `/admin/login` and `/admin/setup` requires a valid session; without one it answers `307` (or `302`/`303`) to `/admin/login…`. `/admin/setup` answers `404` unless there are 0 users **and** `?key=` equals `HOLA_PREVIEW_KEY`.
- There is **no JSON API** for content, users or inquiries: `/api/users`, `/api/inquiries` and any other path under `/api/` except the `/api/hola/*` routes in §7 and §16 answer `404`.
- Admin mutations are Server Actions (Next's origin check applies) or `POST` routes that verify the session and role.
- No user called `admin`; the run creates no permanent users.
- No kit file is reachable over HTTP: nothing from `kit/` is copied into `public/` except the brand files listed in `kit/brand/README.md`.
- `.env.local` is never committed, printed or copied.

## §16 Caching and revalidation

- **No database access and no `siteUrl()` during `pnpm build`**: every `generateStaticParams` returns `[]` (including `[locale]/layout.tsx`; keep `dynamicParams = true`); `robots.ts`, `sitemap.ts` and any route reading the database or `siteUrl()` are request-time (`await connection()` or `export const dynamic = 'force-dynamic'`); no module-level queries. Never catch a database error into a rendered, cacheable page. Pages render on demand and are cached (ISR).
- Admin saves call `revalidatePath` for the affected paths; a `site-settings` or `navigation` save revalidates the whole site (`revalidatePath('/', 'layout')`).
- The data layer never calls `revalidatePath` itself (scripts run outside Next); the thank-you page updates `tracked` while rendering, where `revalidatePath` would throw.
- `POST /api/hola/revalidate` with header `x-hola-revalidate: <HOLA_PREVIEW_KEY>` and body `{"all":true}` revalidates the whole site and answers `200 {"ok":true}`; a wrong or missing header answers `401`.
- The thank-you page, search and anything reading `searchParams` is dynamic.

## §18 Admin

A small, server-rendered admin at `/admin` in the brand style (tokens only), with a Spanish / English UI toggle (cookie `hola_admin_lang`), usable on a phone.

**Auth**

- `users`: `email` (unique), `password_hash` (`bcryptjs`, cost 12 — pure JS), `role` (`admin` manages users and settings; `editor` edits content and inquiries), `session_version` (int), `created_at`, `last_login_at`.
- Login at `/admin/login`: email + password; on success set cookie `hola_session` = JWT (HS256, key `APP_SECRET`, claims `sub` user id, `sv` session_version, `exp` 7 days); `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` on HTTPS. Logout clears it. Every admin page re-checks that the user exists and `sv` matches.
- Login rate limit: after 5 failed attempts per `ip_hash` or per email in 15 minutes, refuse with a generic error until the window passes. Stored in the database (`login_attempts`), not in memory (Hostinger stops idle processes).
- First admin: `/admin/setup?key=<HOLA_PREVIEW_KEY>` works only while there are 0 users and creates an `admin`. `pnpm -s hola:setup-url` prints the link.
- **Redirects happen in the interceptor:** for `/admin…` (except `/admin/login` and `/admin/setup`) with a missing or invalid (signature/expiry) `hola_session`, `proxy.ts` answers `307` to `/admin/login?next=<path>`. Pages still re-check the user and `sv`. No `loading.tsx` or Suspense boundary above `redirect()`/`notFound()` in `(admin)` (a streamed 200 cannot become a redirect or 404).
- Passwords: at least 10 characters. Users change their own password; admins add/remove users and reset a password (new one shown once).

**Screens**

| Screen | What it does |
| --- | --- |
| Dashboard | counts, newest inquiries, links |
| Tours, Cruises, Excursions, Destinations, Guides, Pages | list (search, language availability, sample badge) → edit form: shared fields + **ES / EN tabs** for localized fields; create, duplicate, delete (with confirm); "view on site" |
| Taxonomies | the six term lists with their landing fields |
| Images | library grid; edit alt ES/EN; scan `public/images/` for new files |
| Settings | `site-settings` grouped as in §4 |
| Navigation | header items and footer columns, add/remove/reorder |
| Inquiries | list (status filter, newest first), detail with every field, change status, export CSV |
| Users | (admin role) list, add, reset password, delete; change own password |

**Forms:** list fields (itinerary, highlights, FAQ, cabins…) use add/remove/reorder rows, not raw JSON. Relationship fields use searchable selects. Markdown fields use a textarea with a preview. Server-side validation with `zod`; errors shown next to fields. Spec rules (`subtitle` ≤ 90, `highlights` 3–8, `related_trips` ≤ 3, both prices when available, alt required) are enforced on save.

## §19 Hostinger deployment rules

The app is deployed as a **Hostinger Node.js Web App** (Business plan) from the private GitHub repo `AHMED-FAYED701/hola-egipto`, branch `main`. Hostinger installs, builds (`build` script, output `.next`) and starts it.

- **`next.config.ts` exports a plain object** (no function export, no async) with `output: 'standalone'` (Hostinger forces it anyway; locally `next start` then prints a warning, which is fine). `createNextIntlPlugin()(config)` is fine (it returns an object). Add `experimental.serverActions.allowedOrigins: ['hola-egipto.com', 'www.hola-egipto.com']`.
- `package.json` has `"packageManager": "pnpm@<installed version>"` and `"engines": {"node": ">=22"}`.
- **Behind Hostinger's proxy:** build redirect `Location`s as relative paths or from `siteUrl()`, never from `request.url`'s host; cookies get `Secure` when `SITE_URL` starts with `https`.
- **No database access at build time** (§16). Proof: `DATABASE_URL=mysql://x:x@127.0.0.1:1/x pnpm build` succeeds.
- **Migration procedure** (shared by `pnpm migrate` and startup): open **one dedicated** `mysql.createConnection(DATABASE_URL)` (not the pool); `SELECT GET_LOCK('hola_migrate', 30)` — if not `1`, log and skip; count `__drizzle_migrations` rows (0 if the table is missing); `migrate(drizzle(conn), { migrationsFolder })`; count again (`applied` = after − before); `RELEASE_LOCK`; `conn.end()`.
- **Migrations at startup:** `src/instrumentation.ts` `register()` runs that procedure only when `process.env.NEXT_RUNTIME === 'nodejs'`, `process.env.NEXT_PHASE !== 'phase-production-build'` and `HOLA_AUTO_MIGRATE=1`; logs the result and never crashes the server on failure. `outputFileTracingIncludes: { '/**/*': ['./drizzle/**/*'] }` so the SQL files and `drizzle/meta/` ship with the standalone output; resolve the folder from `process.cwd()`.
- **Database host:** on Hostinger the app connects to `localhost:3306`. From WSL, scripts with `--env=hostinger` connect to the Remote MySQL host shown in hPanel after the owner allows his IP.
- **No native modules at runtime:** `mysql2`, `bcryptjs`, `jose`, `nodemailer`, `marked`, `sanitize-html` are pure JS. `sharp` is a devDependency for placeholders only; never import it from app code.
- **Package manager:** pnpm, `pnpm-lock.yaml` committed, Node 22.
